# 电竞馆智能选址系统 - 需求分析与澄清文档

## 1. 核心业务目标
开发一款支持私有化部署（Docker）的电竞馆智能选址系统。系统基于地图交互，结合内外部数据（高德地图API、POI数据、用户上传的历史运营数据等）以及大模型能力，为用户提供特定地址的评估建议或特定区域内的选址推荐。系统特别支持连锁品牌管理已有门店，避免内部竞争。

## 2. 关键功能模块 (Key Features)
*   **地图交互与可视化**：提供直观的地图界面，支持框选/多边形选定特定区域；支持标记和展示已有连锁店铺的位置。
*   **智能区域推荐**：在用户选定的地图范围内，基于成熟的选址模型（竞品密度、目标客群、交通等），推荐最优的开店坐标点或区块。
*   **单点地址评估**：用户输入或在地图上点击特定地址，系统生成该地址的综合选址评估报告及评分。
*   **连锁门店网络规划**：在推荐新址时，将“已有店铺位置”作为负向或协同因子，避免新店与老店客流内耗。
*   **历史数据赋能**：支持用户上传历史运营数据（如门店位置、营业额、上座率等）。系统在有数据时利用其微调推荐权重（锦上添花），无数据时依赖基础模型正常工作。
*   **高扩展性接口架构**：系统底层设计解耦，预留标准化的大模型（LLM）接入层和外部数据源（如高德地图API、各类商业数据API）接入层。

## 3. 用户故事 (User Stories)
*   **作为电竞馆投资者**，我希望在地图上圈选一个商圈，系统能直接告诉我这里最适合开店的3个具体位置，以便我进行实地考察。
*   **作为连锁品牌拓展经理**，我希望能在地图上看到我们所有已营业的门店，并在系统推荐新址时自动避开我们现有门店的辐射范围。
*   **作为门店运营者**，我希望输入一个我正在看的中介商铺地址，系统能结合周边大学生数量、交通和竞品情况，给我一份详细的评估报告。
*   **作为数据分析师**，我希望能够上传我们过去两年的各门店营收报表，让系统的选址算法能学习到我们品牌独有的成功选址特征。

## 4. 非功能需求 (Non-functional Requirements)
*   **部署方式**：全面支持 Docker 化，提供 `docker-compose.yml`，实现一键本地或云服务器私有化部署。
*   **可扩展性**：采用模块化设计，外部API（高德、大模型）调用需封装为独立的服务类，方便未来切换不同供应商（如从高德换为百度，从OpenAI换为国产大模型）。
*   **数据安全**：由于涉及用户上传的历史商业数据，系统需保证数据的本地隔离，不向外部泄露核心商业机密。

## 5. 技术栈建议 (Suggested Tech Stack)
*   **前端 (Frontend)**：Vue 3 或 React + TailwindCSS + 高德地图 JS API (或 Mapbox GL)。
*   **后端 (Backend)**：Python (FastAPI)。Python 在处理地理空间数据（GeoPandas）、对接大模型以及后续可能的机器学习推荐算法上具有绝对生态优势。
*   **数据库 (Database)**：PostgreSQL + PostGIS 插件。PostGIS 是处理地理空间查询（如“查找多边形内的所有POI”、“计算两点距离”）的行业标准。
*   **部署 (Deployment)**：Docker + Docker Compose。

## 6. 潜在风险 (Potential Risks)
*   **数据获取与成本**：高质量的POI数据（如周边网吧具体数量、高校在校人数、小区入住率）通常需要付费API。若仅依赖免费接口，可能面临调用次数限制或数据不够详实的问题。
*   **“成熟标准”的量化**：选址经验（如“离学校近但不能太偏”）需要转化为精确的数学模型或规则引擎，初期可能需要大量人工调参。
*   **大模型幻觉**：若使用大模型生成评估报告，大模型可能会在缺乏数据支撑的情况下“编造”商圈繁华程度，需要通过严格的 Prompt 工程和 RAG（检索增强生成）技术限制其输出边界。

## 7. 澄清问题 (Clarification Questions)
为了更精准地制定下一步的开发计划，请协助确认以下问题：
1.  **数据源获取**：除了高德API，是否有预算购买专业的商业地产/人口画像数据？如果没有，我们初期将主要依赖免费公开的POI数据（如高德的基础POI检索）。
2.  **成熟的判断标准**：你提到的“成熟的判断标准”具体包含哪些核心维度？（例如：周边3公里大学数量、同类网吧/电竞馆竞品密度、地铁站距离、租金成本等）。
3.  **大模型的作用**：预留大模型接口主要是为了做什么？是用于根据数据自动生成易读的《最终选址评估报告》，还是用于自然语言交互（如用户直接输入“帮我找大学城附近适合开电竞馆的地方”）？
4.  **系统用户角色**：这个系统是仅供你或内部团队使用（单租户），还是计划未来做成SaaS开放给外部客户（多租户，需要复杂的权限管理）？
5.  **历史数据格式**：用户上传的历史运营数据大概包含哪些字段？（如：门店经纬度、面积、机器数量、日均上座率、月营收等），这决定了我们数据导入模块的设计。

## 8. 用户反馈与技术架构深化 (User Feedback & Technical Architecture)

### 8.1 数据源确认
**数据源主要来自**：高德地图 API（POI、热力图、路线规划等）、美团 API（竞品位置、评分、评价等）。系统将以这两个国内主流平台作为核心数据源。

### 8.2 用户上传数据的处理策略 (Critical Architecture Decision)
这是系统的**核心架构问题**。用户上传的历史运营数据需要根据数据类型采用**混合处理策略**：

#### 8.2.1 数据类型与处理方式对应表

| 数据类型 | 示例字段 | 推荐处理方式 | 存储位置 | 说明 |
|---------|--------|-----------|--------|------|
| **结构化数值数据** | 门店经纬度、面积、机器数量、日均上座率、月营收 | 直接存入关系型数据库 | PostgreSQL | 用于数学运算、统计分析、权重调整 |
| **地理空间数据** | 门店位置坐标、服务范围多边形 | PostGIS 地理空间索引 | PostgreSQL + PostGIS | 用于空间查询（如"找出3km内的竞品"） |
| **非结构化文本数据** | 用户备注、运营经验描述、市场分析 | 向量化存储 | 向量数据库（如 Milvus、Weaviate 或 SeekDB） | 用于语义搜索、大模型上下文增强 |
| **时间序列数据** | 日/周/月营收趋势、上座率变化 | 时间序列数据库或 PostgreSQL TimescaleDB 扩展 | PostgreSQL + TimescaleDB | 用于趋势分析、季节性调整 |

#### 8.2.2 混合数据库方案
**推荐采用 SeekDB 或类似的混合数据库方案**，原因如下：
- **SeekDB** 是一款轻量级的混合数据库，支持关系型数据、向量数据、时间序列数据的统一管理。
- 相比分别部署 PostgreSQL + Milvus + TimescaleDB，SeekDB 大幅简化了部署复杂度，更适合私有化部署场景。
- 若采用 SeekDB，则需在系统配置中预留 **SeekDB 连接参数**（主机、端口、认证等）。

#### 8.2.3 向量化与向量模型接口
**向量化流程**：
1. 用户上传非结构化文本数据（如"这家店靠近大学城，周边有3个网吧，租金偏高但客流量稳定"）。
2. 系统调用**向量模型接口**（预留为可配置），将文本转换为向量表示。
3. 向量存储至向量数据库（SeekDB 或独立向量DB）。
4. 在生成选址评估报告时，系统可通过向量相似度检索，找到最相关的历史案例，作为大模型的 RAG 上下文。

**向量模型选项**：
- **本地模型**：使用开源的中文向量模型（如 `sentence-transformers` 的中文模型、阿里的 `text2vec-large-chinese`），部署在本地，无需外部API调用。
- **API 模型**：调用 OpenAI Embeddings、阿里云向量服务等。

**系统需预留的配置**：
```yaml
# 向量模型配置（config.yaml 示例）
vector_model:
  type: "local" | "api"  # 本地模型或API
  if_local:
    model_name: "sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2"
    device: "cpu" | "cuda"
  if_api:
    provider: "openai" | "aliyun" | "other"
    api_key: "${VECTOR_API_KEY}"
    endpoint: "https://..."
```

### 8.3 大模型集成方案 (LLM Integration)
系统需支持**本地大模型**和**大模型 API** 两种模式，并通过配置文件灵活切换。

#### 8.3.1 大模型的应用场景
- **选址评估报告生成**：基于结构化数据（竞品数、人口密度等）和向量检索的历史案例，由大模型生成易读的评估报告。
- **自然语言交互**（可选）：用户可用自然语言描述需求（如"帮我找大学城附近适合开电竞馆的地方"），大模型理解意图后调用后端接口。

#### 8.3.2 大模型配置接口
```yaml
# 大模型配置（config.yaml 示例）
llm:
  type: "local" | "api"
  if_local:
    model_name: "qwen2-7b-instruct"  # 本地部署的模型
    base_url: "http://localhost:8000"  # 本地推理服务地址（如 Ollama、vLLM）
    device: "cuda"
  if_api:
    provider: "openai" | "qwen" | "claude" | "other"
    api_key: "${LLM_API_KEY}"
    model: "gpt-4-turbo" | "qwen-max"
    base_url: "https://api.openai.com/v1"  # 支持兼容 OpenAI 的 API
    temperature: 0.7
    max_tokens: 2000
```

#### 8.3.3 本地大模型部署建议
- 使用 **Ollama** 或 **vLLM** 作为本地推理引擎，在 Docker 容器中运行。
- 推荐模型：Qwen 系列（阿里）、Llama 系列（Meta）、ChatGLM 系列（清华）。
- 在 `docker-compose.yml` 中预留可选的大模型服务容器。

### 8.4 数据库连接配置接口 (Database Configuration)
由于系统支持私有化部署，用户可能在不同的环境中部署不同的数据库（本地 PostgreSQL、云 RDS、自建 SeekDB 等），因此需要**完整的数据库配置接口**。

#### 8.4.1 数据库配置方案
```yaml
# database.yaml 示例
database:
  type: "seekdb" | "postgresql"
  
  if_seekdb:
    host: "${DB_HOST:localhost}"
    port: "${DB_PORT:8888}"
    username: "${DB_USER}"
    password: "${DB_PASSWORD}"
    database: "${DB_NAME:esdb}"
  
  if_postgresql:
    host: "${DB_HOST:localhost}"
    port: "${DB_PORT:5432}"
    username: "${DB_USER}"
    password: "${DB_PASSWORD}"
    database: "${DB_NAME:esdb}"
    extensions: ["postgis", "timescaledb"]  # 启用扩展
    ssl_mode: "disable" | "require"

vector_db:
  type: "seekdb" | "milvus" | "weaviate"  # 若使用独立向量DB
  host: "${VECTOR_DB_HOST:localhost}"
  port: "${VECTOR_DB_PORT:19530}"
  # ... 其他连接参数
```

#### 8.4.2 环境变量与配置优先级
- **优先级**：环境变量 > 配置文件 > 默认值
- **Docker 部署**：通过 `.env` 文件或 `docker-compose.yml` 中的 `environment` 字段传入配置。
- **本地开发**：通过 `.env.local` 或 `config/local.yaml` 覆盖默认配置。

#### 8.4.3 配置管理模块
系统需提供**配置管理后台**（或 CLI 工具），让用户能够：
- 验证数据库连接是否正常。
- 初始化数据库表结构和索引。
- 切换不同的 LLM 和向量模型。
- 查看当前系统配置状态。

### 8.6 用户数据上传与处理流程 (Data Upload & Processing Pipeline)

#### 8.6.1 数据导入流程
```
用户上传 CSV/Excel
    │
    ▼
数据验证 & 类型推断
    │
    ├─ 结构化数值 → PostgreSQL
    ├─ 地理坐标 → PostGIS 索引
    ├─ 文本描述 → 向量化 → 向量DB
    └─ 时间序列 → TimescaleDB
    │
    ▼
数据融合与权重调整
    │
    ▼
更新推荐模型参数
```

#### 8.6.2 数据导入模块的关键功能
- **格式检测**：自动识别 CSV、Excel、JSON 等格式。
- **字段映射**：用户可自定义上传文件中的字段与系统内部字段的对应关系。
- **数据清洗**：去重、缺失值处理、异常值检测。
- **向量化**：对文本字段自动调用向量模型进行向量化。
- **增量更新**：支持增量导入，而不是每次全量覆盖。
